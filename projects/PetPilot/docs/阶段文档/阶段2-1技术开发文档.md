# 第 2-1 阶段技术开发文档｜后端地基 + 文字记录核心闭环

> 配套文档：`docs/PRD/一页纸MVP.md`（以它为准）、`docs/PRD/宠物合伙人_MVP规则映射与提示词.md`、AI Agent 产品 Vibe Coding 通用技术栈手册。
> 本文档只覆盖阶段 2-1。AI 开发时不得提前实现其他阶段的能力。

## 一、阶段目标

- **交付范围**：后端工程骨架 + 固定验证码登录 + 猫档案 + "发一句话 → 分猫 → 归档 → 真实回执 → 历史查询"这条文字记录主链路。
- **阶段产物**：可一条命令启动的 FastAPI 后端；临时验收界面（`backend/static/index.html` 文字聊天页）；mock 测试全过；`scripts/restart-check.sh` 重启恢复验证。
- **验收标准**（对齐 PRD §9 的 1/2/4 条，本阶段子集）：
  1. 一条命令起服务；
  2. 用 mock 走通：保存记录、多猫不串、历史查询；
  3. 重启后数据还在（`restart-check.sh` 验证）。
- **明确不做**（后续阶段，防蔓延）：纠错（2-2）、提醒/任务（2-2）、就医摘要+模拟医院回复（2-2）、照片上传（2-2）、周回顾（2-3）、语音转文字（阶段 3 前端）、删除能力（二期）、真实模型冒烟（2-1 用 mock，真实 DeepSeek 冒烟在收口阶段做）。
- **本阶段打通的主链路片段**：登录 → 发一句话 → 模型拆解 → 服务端裁决分猫 → 落库 → 回执 → 历史查询。

## 二、技术适配摘要

- 引用《技术适配声明》结论：后端先行 + 临时验收界面。
- 本阶段采用默认方案：Python 3.12 + FastAPI + Pydantic + pytest + Git + SQLite + SQLAlchemy + Alembic + DeepSeek（OpenAI 兼容接口）。
- 本阶段启用按需模块：本地文件目录（照片 2-2 用，本阶段先建结构）；持久化任务记录（提醒 2-2 用，本阶段不建）。
- 本阶段偏离/暂缓：SSE 流式本阶段先不引入（模型单次调用几秒内完成，`POST /api/messages` 同步返回；2-2 若需流式展示再引入）。
- 开发路径：后端先行。

## 三、技术栈与模型

- 后端：FastAPI + Uvicorn；数据：SQLite + SQLAlchemy + Alembic；校验：Pydantic；测试：pytest + httpx。
- 模型：DeepSeek `deepseek-chat`，`response_format={"type":"json_object"}` 强制 JSON 输出；通过 OpenAI 兼容 SDK（`openai` 包，`base_url=https://api.deepseek.com`）。不引入 OCR / ASR / 短信 / COS / 任务队列 / Chroma / Word / PDF。

## 四、环境与配置

- 不含秘密的配置放 `backend/.env.example`：`MODEL_BASE_URL`、`MODEL_NAME`、`MODEL_API_KEY`（占位）、`FIXED_LOGIN_CODE`、`DATABASE_URL`。
- 需要产品经理提供：**DeepSeek API Key**（验收前提供即可，开发期用 mock）；填到 `backend/.env` 的 `MODEL_API_KEY` 一行。
- 启动：`backend/.venv`（Python 3.12.14），`uvicorn app.main:app --port 8000`；后端 8000，临时界面由 FastAPI 挂载在 `http://localhost:8000/`。

## 六、数据、资产与状态

- 持久化方式：SQLite（数据量小，PRD 指定不上 PG）；读写集中在 `repository.py`，上线时切云开发 PostgreSQL HTTPS 网关。
- 数据表（001_init）：

| 表 | 字段 | 说明 |
| --- | --- | --- |
| sessions | token(PK)、created_at | 固定验证码换的登录令牌，重启后仍在（演示友好） |
| pets | id(PK)、name(唯一)、created_at | 猫档案 |
| messages | id(PK)、role、content、created_at | 原始用户消息/助手回复 |
| facts | id(PK)、pet_id(FK)、topic、value、unit、quantity_scope、historical_current、occurred_at、polarity、change_kind、source_message_id(FK)、quote、version(默认1)、created_at | 观察事实；quote 存原文出处；version 供 2-2 纠错递增 |
| held_segments | id(PK)、message_id(FK)、quote、topic、reason、resolved_pet_id(可空)、status、created_at | 归属未知的挂起片段 |

- 资产：本阶段无图片/音频（照片 2-2）；不引入 COS。
- 状态机：`held_segments.status = pending`（本阶段只挂起；2-2 补归属转 resolved）；`facts.version` 从 1 起（2-2 纠错递增）。

## 七、API 设计

> 所有错误统一 `{"error":{"code","message"}}`，不泄露堆栈。需要登录的接口带 `Authorization: Bearer <token>`。

| 方法 | 路径 | 请求 | 响应 | 错误码 |
| --- | --- | --- | --- | --- |
| POST | /api/auth/login | `{"code":"123456"}` | `{"token":"..."}` | AUTH_INVALID_CODE |
| GET | /api/pets | — | `{"pets":[{"id","name"}]}` | AUTH_REQUIRED |
| POST | /api/pets | `{"name":"明月"}` | `{"pet":{"id","name"}}` | PET_NAME_DUPLICATE |
| POST | /api/messages | `{"text":"明月今天吃了26克"}` | `{"message":{...},"facts":[{"id","pet_id","topic","value","unit","quote","version"}],"held_segments":[...],"answer":"...","explanation":"..."}` | MODEL_FAILED / SCHEMA_INVALID |
| GET | /api/messages | — | `{"messages":[...]}` | AUTH_REQUIRED |
| GET | /api/facts?pet_id= | — | `{"facts":[...]}` | PET_NOT_FOUND |
| GET | /api/held | — | `{"held_segments":[...]}` | AUTH_REQUIRED |

- `POST /api/messages` 同步返回（本阶段不用 SSE）。
- 服务端裁决（不交给模型自由决定）：
  1. `pet_id` 必须在已知宠物列表，否则转 held（不得编造 pet_id、不得留空、不得猜当前猫）；
  2. quote 必须完整落在原文里（不拼接不改写），校验失败丢弃该 operation；
  3. 明确表达优先：原文整词匹配到已知猫名但模型给了 hold 时，服务端纠正归属；
  4. 只有落库成功才在 answer 里回"已保存"（模型文字禁止自称成功）；
  5. 即时观察无日期 → 按消息所在时区的当天（R19）。

## 八、Prompt 设计

- 角色/输入/约束以 `宠物合伙人_MVP规则映射与提示词.md` 第二节系统提示词为起点；本阶段只保留 2-1 动作子集：`add_observation`、`hold_segment`、`dialogue.updates/answer/explanation/fact_ids`，删除 `correct_fact`（2-2）、`reminders/task_results/care_requests`（2-2）。
- 输出格式：JSON（`response_format=json_object`），信封结构见规则映射第三节；服务端用 Pydantic 校验，不合法时触发一次重试，仍失败返回 `SCHEMA_INVALID`。

## 九、验收界面

- 需要最小界面（Agent 产出是结构化 JSON，产品经理须"打字→看分猫/回执"判断质量）。
- 类型：**临时验收界面**（`backend/static/index.html` 单文件，原生 JS + fetch，阶段 3 开始时废弃，是否表第 4/7 项对它填 N/A）。
- 功能上限：登录、选猫、发文字、看回执/挂起片段/历史；不做移动端适配、不进生产构建。

## 十、测试要求

- 第一层 mock 测试（pytest，`MODEL_API_KEY=""` 时跑，模型走 mock）：
  1. 登录：正确码→token；错码→401；
  2. 建猫/列猫：成功；重名→PET_NAME_DUPLICATE；
  3. 分猫：单猫明确；多猫拆段各归各主；同名猫独立；歧义挂起；界面选中明月时"贝塔拉稀"仍记贝塔（不串猫）；
  4. 归档：add_observation 落库；quote 不合法被丢弃；pet_id 编造被拒并转 held；
  5. 回执：落库成功才含"已保存"；
  6. 失败处理：模型失败/超时→返回 MODEL_FAILED、保留输入、可重试、不假保存；
  7. 重启恢复：写 fact 后重启→数据还在（`scripts/restart-check.sh`）。
- 第二层真实冒烟：本阶段收口用真实 DeepSeek 走"明月今天吃了26克，贝塔有点拉稀"→两猫各记各的（无 Key 时记"待验"）。
- `scripts/restart-check.sh`：本阶段首次新建。

## 十二、风险与待确认项

- 风险：DeepSeek 结构化输出偶尔不合法 → 服务端 schema 校验 + 一次重试 + 兜底错误；归属歧义 → 挂起而非乱猜。
- 已知限制：本阶段界面只支持文字（照片/语音后续阶段）；固定验证码仅合成体验空间，非真实登录方案。
- 待产品经理决定的问题：无。

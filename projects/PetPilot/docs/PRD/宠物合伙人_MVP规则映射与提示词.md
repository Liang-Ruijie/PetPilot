## 二、MVP 版系统提示词（从旧项目提炼，已删医院/费用/知识/外发）

> 以下从 `model_client.py` 提炼，删掉了 MVP 不需要的 `external_requests / estimate_drafts / suggested_tasks / report_ids / knowledge_ids / cooperation`。
> 可直接作为 starter-kit 阶段 2 的模型系统提示词起点。

```
你是宠物合伙人 Personal Agent，服务猫主人的持续助理。把用户消息拆成增量操作，严格按 Schema 输出 JSON。

铁律：
0. message_id 与 op_id 由服务端注入，你无需输出；start/end 与 quote 保持一致，不确定可写 0/0，服务端按 quote 定位。
1. pet_id 只能是「允许的宠物身份」里列出的 ID；不在列表或无法确认归属时，用 hold_segment（保留原文），reason 写「归属未知」。不得编造 pet_id、不得留空、不得猜成当前宠物。
2. 明确出现多只猫时拆成多个片段，各归各主；只有无法归属的片段才挂起。归属未知只影响「属于哪只猫」，不得丢掉原文已明确的 topic/数量/单位/范围/时间。
3. 极性 polarity 表示主题的陈述状态，不是情绪好坏：「没精神」=状态+negative（明确陈述精神不佳）；「没有呕吐」=呕吐+negative；「大约吃了一半」保留近似表达与未知基数，不编造克数。
4. quantity_scope 按原文动词判断：吃/喝/摄→intake，放/给/倒/盛→provided；数量或单位缺失时保留为空，不因缺数量把类型改成 unknown。
5. 结构化字段能确定才填，不擅自补全：
   - value/unit：数值与单位（克/g/kg）
   - historical_current：「以前100克」=historical，「今天20克」=current
   - occurred_at：有明确日期就保留日期精度（如 YYYY-MM-DD）；「今天」按消息时间与时区换算；无明确日期时间才省略
   - change_kind：new / supplement / correction / remeasure / repeat
6. 纠错：目标唯一就输出 correct_fact（引用 fact_id + expected_version），不能用 add_observation 冒充修订；quote 从明确宠物名字开始、保留到新值的连续原文，不拼接不改写；歧义输出 hold_segment。
7. 问候、能力咨询、澄清可以输出空 operations，同时用 dialogue.answer 自然回答；含观察信息的输入必须给操作，不能用回答代替归档。
8. 「好的/行/知道了」是结束语，不是授权，不得据此建任务、批准动作或标完成。
9. 明确提醒指令（对象+时间清楚）才输出 dialogue.reminders；只有日期没有具体时间时，由程序按缺信息追问，你不擅自加默认时间；否定/引用/假设/问句不算授权。日期时间由程序解析，你不声称已执行。
10. 就医准备（如「整理成就医摘要，先给我核对，不要发医院」）输出 dialogue.care_requests，只整理内部摘要，**绝不发送或选择医院**；fact_ids 只能引用本猫可见资料。
11. 照片只作为「原图 + 主人提供的描述」保存，你不自动理解图片内容，不生成健康判断。
12. 你不得写「已保存/已记录/已整理/已安排/已发送/已预约/已接诊/确诊/建议服用/剂量/已治愈」等动作结果或诊断处方——成功结果由服务器验证后另行反馈。
13. 一票阻断红线：跨猫/跨账户泄露、编造数值/报告/价格、无授权外发或消费、假保存、删除后仍用、取消后恢复旧安排、药量自主建议。
```

## 三、MVP 版模型输出 schema（信封）

> 以下示例是**示意样例**，不是可校验合同；只包含本期保留的动作类型，不新增动作。

```json
{
  "operations": [
    {"op_id":"a","kind":"add_observation","start":0,"end":6,"quote":"原文片段","pet_id":"猫ID","topic":"进食","value":20,"unit":"克","quantity_scope":"intake","historical_current":"current","occurred_at":"2026-11-04","polarity":"positive","change_kind":"new"},
    {"op_id":"b","kind":"correct_fact","start":0,"end":8,"quote":"明月是吃了40克，不是20克","fact_id":"逻辑ID","expected_version":1,"pet_id":"猫ID","topic":"进食"},
    {"op_id":"c","kind":"hold_segment","start":0,"end":6,"quote":"贝塔有点拉稀","reason":"归属未知","topic":"状态"}
  ],
  "dialogue": {
    "updates": [
      {"pet_id":"猫ID","answers":{"onset":"从今天早上开始"},"concern":true,"status":"open"}
    ],
    "reminders": [
      {"pet_id":"猫ID","quote":"明天上午九点提醒我给明月称重"}
    ],
    "task_results": [
      {"task_id":"任务ID","outcome":"done","note_quote":"已经称好了，32克"}
    ],
    "care_requests": [
      {"pet_id":"猫ID","quote":"帮我整理一下贝塔这次的就医摘要，先不要发","title":"贝塔就医准备","fact_ids":["事实ID1","事实ID2"]}
    ],
    "fact_ids": ["事实ID1"],
    "answer": {"kind":"clarification","text":"请确认这条观察属于明月还是贝塔。"},
    "explanation": {"text":"你记录过明月最近三次进食分别是20克、26克、24克；是否异常需要结合医生检查确认。"}
  }
}
```

### 字段说明（MVP 保留的子集）

**operations（三选一或组合）：**
- `add_observation`：新增观察。可选：topic / value / unit / quantity_scope / historical_current / occurred_at / polarity / change_kind / unknown_fields
- `correct_fact`：纠错。必填 fact_id + expected_version；quote 从明确猫名起连续引用到新值
- `hold_segment`：归属不明挂起。必填 reason=归属未知；可选结构化字段（保留原文已明确信息，供后续办）

**dialogue（可选）：**
- `updates[]`：追问/暂停状态。`answers` 只填本轮明确回答的字段（onset/intake/companions），没提及就省略；`unknown` 只表示用户明确说不知道；暂停用 `status:"paused"` + `status_quote`
- `reminders[]`：主人本轮明确交代的提醒。quote 必须是完整原话子句，不能截掉否定/引用；只有日期没时间→程序追问，不加默认时间
- `task_results[]`：回收上下文任务结果。`outcome` 为 done/feedback；含糊的「好了/好的」不能标 done
- `care_requests[]`：只准备内部就医摘要，不发送不选医院
- `fact_ids[]`：解释/回答引用的当前可见事实 ID
- `answer`：自然回答（kind=conversation/clarification），**不得写动作结果**（不写"已整理/已保存/已安排"）
- `explanation`：有引用的短解释（必须与 fact_ids 并列），不得作诊断处方，无比较标准时不下"偏低/偏高"结论

**MVP 已删除的字段（旧项目有、本期不做）：**
`external_requests`（医院授权外发）、`estimate_drafts`（费用参考）、`suggested_tasks`（报告推导建议提醒）、`report_ids`（报告比较）、`knowledge_ids`（知识库）。

## 四、服务端仍需裁决的确定性规则（不交给模型）

以下逻辑在旧项目里由 `dialogue.py` 用代码裁决，MVP 也必须**由服务端代码实现**，不能只靠提示词：

1. **提醒意图**：否定/引用/假设/问句不算授权（`reminder_intent` 的正则裁决）
2. **quote 校验**：提醒、纠错、任务反馈的 quote 必须完整落在原文里，不能截掉否定词或引用上下文
3. **多猫归属**：明确表达优先；整词匹配（避免「贝塔」匹配「贝塔2」）；歧义挂起
4. **回答边界**：多猫时回答只核对本猫的原话范围，不借用另一猫答案
5. **动作结果**：只有服务端真实落库/执行后才回「已保存/已安排」，模型文字禁止声称成功
6. **纠错版本**：correct_fact 带 expected_version，版本冲突不静默覆盖
7. **日期规则**：即时观察没写日期→按消息所在时区的当天（R19）；明确日期按原话保留；历史时间不明→保留未知，不补具体时刻

> 这些是"可信执行"的底线：模型只提理解，**服务端裁决**，正是旧项目做得对、新 MVP 必须保留的部分。

### 补充：规则与记忆的分工（2026-11-06）

模型后续会加入"最近对话历史"作为上下文（见《记忆承接设计说明》），这**不会**让上述确定性规则作废：

- **安全底线规则（上表 1–7）永远保留**：模型有记忆也会偶尔犯错，防串猫、防假保存、防重复执行、版本校验、时间追问、quote 校验都必须由服务端代码兜底。
- **关键词式"猜意图"补丁**（如"整理 / 建好 / 发送"这类在文字里找关键词）会被"记忆理解短答"部分取代，但保留作兜底。
- 一句话原则：**记忆负责听懂主人，规则负责保证不出错**；不允许以"有记忆了"为由删除任何安全底线规则。

## 五、MVP 必要验收（只验本期保留能力）

只针对已保留能力列**正常用例 + 反例**；不建评测平台、不搬全部旧测试、不用测试数量代替产品可用性结论。

| 能力 | 正常用例 | 反例 |
|---|---|---|
| 分猫 | "明月今天吃了20克，贝塔有点拉稀"→两猫各记各的 | 界面选中明月时，"贝塔拉稀"仍记到贝塔，不串猫 |
| 纠错 | "刚才明月是40克，不是20克"→更新同一条，保留版本来源 | 不能新增一条40克让20克仍影响结论 |
| 提醒授权 | "明天上午九点提醒我给明月称重"→建任务 | "别提醒我称重"、"如果明天…"、"医生说提醒"→不建任务 |
| 真实保存 | 真实 AI 输入→服务端落库后才回执"已保存" | 服务端未成功时，模型文字不得说"已保存/已安排" |
| 失败处理 | 模型失败/超时→保留输入、明确提示、可重试 | 不假保存、不静默丢输入 |
| 重启恢复 | 建提醒后重启服务→任务仍在、只执行一次 | 重启后任务丢失或重复执行 |

> 以上六项是 MVP "可以施工、可以验收" 的最小闭环；真实 AI 验收走通它们，才算完成（mock 仅用于开发验证）。
